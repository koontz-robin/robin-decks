1. Executive summary

COEO / NetWolves can feasibly move the NetWolves service operation from Autotask to New Rev.io and implement a direct SolarWinds-to-Rev.io integration without waiting for the separate billing migration. The recommended path is to stand up ticketing independently, migrate the minimum active customer/site context needed for ticket operations, and build the SolarWinds connector directly into Rev.io rather than invest in a temporary SolarWinds-to-Autotask bridge.

The latest discovery agreement materially narrows the first release from the broader “intelligent intake platform” described in earlier requirements and Exhibit A. The immediate objective is a base-level integration that matches, at minimum, the current Autotask/SolarWinds operating behavior:

✓

Create Rev.io tickets from SolarWinds monitoring alerts.

✓

Populate agreed alert, device/node, site-account, and lifecycle fields.

✓

Match each alert to the correct Rev.io customer/site using the site account identifier.

✓

Update and automatically close eligible tickets when SolarWinds reports recovery/clear.

✓

Prevent duplicate ticket creation from retried delivery of the same source event.

✓

Retain traceable integration logs and route mapping failures for review.

Rev.io’s initial engineering estimate is approximately three development weeks for this base connector, assuming timely SolarWinds sandbox access, representative payloads, agreed mappings, and available client subject-matter experts. A short UAT/pilot period should follow, producing an estimated four calendar weeks from kickoff to controlled production use. If kickoff occurs the week of November 2, 2026, a December 1 pilot/Phase 1 target is achievable but remains dependent on prerequisites and rapid client decisions.

Advanced deduplication, site/topology correlation, parent/child incident grouping, maintenance-window handling, intelligent flood control, Salesforce Case synchronization, email classification, and external customer ticket-system connectors should be treated as later phases—not acceptance conditions for the three-week base connector.

Recommendation

Proceed with a direct, phased Rev.io implementation. Contract Phase 1 around a narrow and demonstrable SolarWinds lifecycle, put enhanced orchestration behind separately estimated options, and re-baseline Exhibit A so acceptance and payment gates match the October 27 agreement.

3. Proposed solution

3.1 Target operating model

SolarWinds remains the monitoring source. New Rev.io becomes the operational ticketing system for the NetWolves service team. A Rev.io-managed integration adapter receives or retrieves SolarWinds events, applies Phase 1 mapping and lifecycle rules, and invokes supported Rev.io ticket APIs.

Logical flow
1

SolarWinds emits an alert/open, update, or recovery/clear event.

2

The integration validates the payload and captures the SolarWinds event identifiers.

3

The integration resolves the Rev.io customer/site using the SolarWinds site account number and agreed cross-reference table.

4

The integration creates or updates a ticket with structured monitoring fields.

5

A recovery event updates the ticket and automatically closes it only when the configured Phase 1 eligibility rules are met.

6

Failures are retried; unresolved customer/site mappings enter an exception queue or report.

7

Integration telemetry records the source event, decision, Rev.io ticket ID, result, retry status, and timestamp.

The implementation mechanism may be Prismatic or another Rev.io-managed integration runtime. The detailed design should favor a thin, supportable adapter for Phase 1 rather than prematurely building the full intelligent-orchestration platform described in the earlier requirements.

3.2 Phase 1 data model

At minimum, tickets should retain the following structured values when supplied by SolarWinds:

✓

SolarWinds alert object ID (AOID) and event/state identifier.

✓

SolarWinds node ID, node name, and applicable interface/device identifier.

✓

Site account number and resolved Rev.io customer/site ID.

✓

Alert name/type, alert state, severity/custom priority if adopted, and monitored condition.

✓

Opened, last-updated, and recovered/cleared timestamps.

✓

Device/service context available in the alert payload.

✓

Integration source, integration processing status, and automated-update indicator.

Final field mapping is a design deliverable. The client should provide representative payloads and the current Autotask ticket examples used as the minimum parity baseline.

3.3 Ticketing onboarding approach

Ticketing onboarding should run in parallel with connector development and should not depend on billing migration.

Recommended sequence:
✓

Stand up a dedicated New Rev.io test/sandbox environment.

✓

Import active customers/sites and the identifiers required for SolarWinds mapping.

✓

Configure ticket types, statuses, priorities, queues, roles, SLAs, email templates, and monitoring custom fields.

✓

Migrate or archive historical Autotask ticket data through a separate data workstream so it does not delay the integration pilot.

✓

Preserve identifiers needed for future consolidation, but do not introduce a real-time Autotask sync.

3.4 Volume and burst handling

The previously raised Rev.io ingestion-capacity concern is considered resolved for feasibility purposes. Phase 1 should still include a representative load test that validates the agreed sustained and burst profiles, including retry behavior and duplicate-delivery handling.

This test is intended to prove the implementation, not to reopen the platform-feasibility decision. Exact test volumes, payload mix, success criteria, and observation window should be documented during design.

6. Phase 1 acceptance criteria

Phase 1 should be accepted when all agreed scenarios pass in the client test environment and the controlled pilot. Suggested criteria:

1

Connectivity: SolarWinds and Rev.io authenticate using approved non-user integration credentials or the approved supported mechanism.

2

Create: A valid SolarWinds alert creates a Rev.io ticket with all mandatory mapped fields.

3

Account/site resolution: A valid site account number resolves to the correct Rev.io customer/site.

4

Lifecycle update: A subsequent event for the same source alert updates the intended ticket according to the Phase 1 key.

5

Recovery: A clear/recovery event records the recovery data and auto-closes the ticket when eligibility rules are met.

6

Technician protection: The integration does not auto-close a ticket in any excluded technician-controlled status.

7

Idempotency: Re-delivery of the same source event does not create an unintended duplicate ticket.

8

Exception handling: Missing or ambiguous account/site mappings are retained and surfaced for correction; events are not silently discarded.

9

Retry and audit: Transient failures retry, and the source event, action, result, ticket ID, timestamp, and error state are traceable.

10

Performance: The agreed sustained and burst test completes within the agreed latency/error thresholds without event loss.

11

Operational readiness: Runbook, monitoring, rollback, escalation path, and support ownership are approved.

12

Parity demonstration: The agreed minimum examples from the current Autotask/SolarWinds process are demonstrated in Rev.io.

Numerical thresholds—latency, burst volume, acceptable error rate, retry window, and stabilization period—must be agreed during design rather than inferred from the broader Exhibit A.
